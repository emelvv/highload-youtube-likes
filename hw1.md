## Назначение и границы системы

Сервис хранит реакции пользователей на видео и показывает общее число лайков. Зритель видит популярность видео, а автор видео получает тот же публичный счётчик для своих публикаций. Главную нагрузку создаёт чтение счётчика при открытии видео; изменения реакций происходят реже, но требуют защиты от повторного учёта.

В проект входят чтение общего числа лайков, получение собственной реакции, установка и снятие лайка. Видеохостинг предоставляет идентификаторы существующих видео и проверенную идентичность пользователя. Воспроизведение и загрузка видео, рекомендации, комментарии, дизлайки и проверка пользовательских паролей находятся за границами этого сервиса.

Это учебный сервис с поведением счётчика лайков. Все значения нагрузки, задержек, доступности и восстановления ниже являются выбранными проектными требованиями, а не сведениями о реальном YouTube. Они задают условия для последующих расчётов и экспериментов; достигнутая производительность на этапе ДЗ1 не утверждается.

## Роли пользователей

| Роль | Взаимодействие с сервисом |
|---|---|
| Неавторизованный зритель | Читает публичное число лайков существующего видео. Для просмотра счётчика вход в аккаунт не требуется. |
| Авторизованный зритель | Читает счётчик и свою реакцию, ставит и снимает собственный лайк. Идентификатор пользователя берётся из проверенной авторизации; изменять чужие реакции нельзя. |

Автор видео использует права зрителя: может читать счётчик своего видео и управлять только собственной реакцией. Владение видео не даёт ему права исправлять общий счётчик или реакции других людей. Отдельная роль автора не нужна, поскольку в границах проекта у неё нет дополнительных действий.

## Сценарии использования

### S1 Получить общий счётчик

**Главный сценарий по нагрузке.** Неавторизованный или авторизованный зритель открывает видео. Видеохостинг запрашивает число лайков по идентификатору видео и показывает результат. Ответ содержит неотрицательное целое число и время актуальности счётчика. Отсутствие лайков у существующего видео даёт значение 0; неизвестный идентификатор видео даёт ошибку, а не ложный нулевой счётчик.

Сценарий создаёт основную нагрузку чтения. Особенно важен случай популярного видео, к которому одновременно обращаются многие зрители.

### S2 Поставить лайк

Авторизованный зритель нажимает кнопку лайка. Сервис устанавливает активную реакцию для пары «пользователь — видео» и подтверждает сохранённое состояние с его версией. Если реакция уже активна, дополнительный лайк не возникает. Интерфейс сразу отображает личное состояние; общий счётчик обновляется в пределах заданного срока распространения изменений.

Повторная отправка того же действия после сетевого таймаута возвращает результат исходной операции и не выполняет изменение ещё раз.

### S3 Снять лайк

Авторизованный зритель отменяет свой лайк. Сервис переводит его реакцию в неактивное состояние и возвращает подтверждение с версией. Если лайка уже нет, операция остаётся успешной и не уменьшает счётчик повторно. Общее число лайков после распространения изменения уменьшается на один только при переходе из активного состояния в неактивное.

### S4 Получить собственную реакцию

Авторизованный зритель открывает видео или возвращается к нему с другого устройства. Сервис возвращает только реакцию этого пользователя: «лайк установлен» или «лайк не установлен», а также её версию. Данные о том, кто ещё поставил лайк, не раскрываются.

После успешной S2 или S3 клиент может передать версию подтверждённого изменения. Тогда S4 возвращает состояние этой версии или более новой. Если требуемая версия недоступна, сервис отвечает ошибкой, а не успешным устаревшим состоянием.

## Функциональные требования

| ID | Требование | Связанные сценарии |
|---|---|---|
| FT1 | Показывать публичный счётчик существующего видео всем зрителям, включая пользователей без авторизации. | S1 |
| FT2 | Хранить для каждой пары «пользователь — видео» ровно одно логическое состояние реакции: активна или неактивна. Активная реакция даёт один лайк. | S2, S3, S4 |
| FT3 | Разрешать установку и снятие реакции только от имени авторизованного пользователя. Идентификатор из тела запроса не может подменить пользователя из авторизации. | S2, S3 |
| FT4 | Установка уже активной реакции и снятие уже неактивной реакции не должны изменять итоговое число лайков. | S2, S3 |
| FT5 | Принимать идентификатор операции для S2 и S3 и распознавать её повторную отправку в течение 24 часов после подтверждения. Повтор не выполняется заново, в том числе после более нового изменения этой пары. Использование того же идентификатора с другими параметрами даёт ошибку конфликта. | S2, S3 |
| FT6 | Упорядочивать изменения одной пары и выдавать монотонно возрастающую версию при изменении состояния. Для одновременных различных действий итог соответствует последнему принятому изменению. Клиент не заменяет более новую версию состояния более старой из запоздавшего ответа. | S2, S3, S4 |
| FT7 | Предоставлять пользователю чтение собственной реакции, включая возможность потребовать версию не ниже указанной. | S4 |
| FT8 | Считать общее число лайков как количество активных реакций разных пользователей данного видео. Итог не может быть отрицательным. Временно устаревшее значение допустимо только в пределах требований к свежести. | S1, S2, S3 |
| FT9 | Различать ошибки авторизации, отсутствующее видео, конфликт идентификатора операции и временную недоступность. При отсутствии возможности надёжно подтвердить изменение возвращать ошибку; успешный ответ о сохранении не имитировать. | S1–S4 |

Дедупликация по идентификатору операции действует 24 часа. Клиент не повторяет исходную операцию позднее этого срока; он сначала читает текущее состояние и при необходимости создаёт новое действие. Идемпотентность не означает одновременную доставку запросов и не устраняет необходимость упорядочить разные действия.

## Профиль нагрузки

Для проектирования принимаются **5 млн активных пользователей в сутки** и каталог до **50 млн существующих видео**. Начальное число активных реакций — 1 млрд; требования должны выполняться при объёме до 1,2 млрд активных реакций. Суточное число операций и их пики являются учебными допущениями.

| Сценарий | Операций на одного активного пользователя в сутки в среднем | Операций в сутки | Средняя нагрузка | Целевой пик |
|---|---:|---:|---:|---:|
| S1 Общий счётчик | 20 | 100 млн | 1 157,4 запросов/с | 12 000 запросов/с |
| S2 Установить лайк | 1 | 5 млн | 57,9 запросов/с | 1 200 запросов/с |
| S3 Снять лайк | 0,2 | 1 млн | 11,6 запросов/с | 250 запросов/с |
| S4 Своя реакция | 4 | 20 млн | 231,5 запросов/с | 3 000 запросов/с |

Средняя нагрузка рассчитана как число операций в сутки, делённое на 86 400 секунд. Всего получается 126 млн операций в сутки, примерно 1 458,3 запросов/с в среднем. S1 составляет около 79,4% суточных обращений и поэтому выбран главным сценарием.

Пики задаются отдельно от средних значений. Сервис должен выдерживать одновременные пики всех четырёх сценариев — **16 450 запросов/с в течение 30 минут** — с выполнением требований к задержке и свежести. Повторные обращения и ретраи входят в указанные лимиты запросов/с, а не добавляются сверх них.

Внутри этого пика одно популярное видео может получать до **5 000 запросов/с** к общему счётчику и до **500 изменений реакций/с** суммарно по S2 и S3. Эти значения входят в общий пик. Такое распределение должно проверяться отдельно: равномерное распределение обращений между видео не является достаточным условием выполнения требований.

## Требования к задержке

Задержка измеряется на входе API: от получения полного запроса до отправки полного ответа. Она включает проверку авторизации, обращения к зависимостям и ожидание подтверждения сохранения. Передача по пользовательскому интернету, DNS и установление соединения до отправки запроса в эту метрику не входят.

| Сценарий | p50 не более | p95 не более | p99 не более | Предельное время успешного ответа |
|---|---:|---:|---:|---:|
| S1 Общий счётчик | 30 мс | 100 мс | 250 мс | 500 мс |
| S2 Установить лайк | 60 мс | 180 мс | 500 мс | 1 000 мс |
| S3 Снять лайк | 60 мс | 180 мс | 500 мс | 1 000 мс |
| S4 Своя реакция | 40 мс | 120 мс | 300 мс | 1 000 мс |

Например, p99 ≤ 250 мс означает, что не менее 99% успешных запросов данного сценария завершаются за 250 мс. Перцентили рассчитываются отдельно для каждого сценария на интервалах 5 минут при нагрузке не выше указанного пика и при установленном объёме данных. Проверяется и общий поток S1, и поток обращений к популярному видео.

Ошибки не подменяют быстрые успешные ответы: таймауты, ответы с ошибкой и ответы, не удовлетворяющие требованиям свежести, учитываются в доступности. При оценке нагрузки нужны как распределение задержек успешных ответов, так и доля неуспешных запросов.

## Доступность и поведение при сбоях

| Сценарий | Целевая доступность за календарный месяц |
|---|---:|
| S1 Общий счётчик | Не менее 99,95% |
| S2 Установить лайк | Не менее 99,9% |
| S3 Снять лайк | Не менее 99,9% |
| S4 Своя реакция | Не менее 99,9% |

Доступность сценария равна доле корректных допустимых запросов, которые получили успешный ответ за предельное время из таблицы задержек и с соблюдением требований к содержимому. Она измеряется отдельно для каждого сценария. Ошибки клиента, например неверная авторизация или неизвестное видео, не входят в знаменатель. Внутренние ошибки, таймауты и отказ обслужить допустимый запрос из-за перегрузки в пределах заданного профиля входят в число неуспешных запросов.

Плановые технические работы также учитываются в доступности. Во время аварии и восстановления допустимые запросы продолжают учитываться в доступности. Ответы, нарушающие предельное время или обычные требования к свежести, считаются неуспешными. Целевые p50/p95/p99 проверяются отдельно для штатной работы.

При отказе одного узла или одной зоны размещения сервис должен восстановить обслуживание чтения общего счётчика не позднее чем за **1 минуту после возникновения отказа**, а операций с собственной реакцией — не позднее чем за **5 минут после возникновения отказа**. Это верхние границы длительности отдельного восстановления; они не разрешают превышать месячный бюджет ошибок.

Если при разделении сети невозможно надёжно принять изменение или подтвердить требуемую версию личной реакции, сервис возвращает временную ошибку, например `503`. Успешный ответ не выдаётся ценой нарушения требований к реакции. Неуспешные допустимые запросы при таком сбое учитываются в доступности.

## Согласованность и свежесть данных

**Собственная реакция.** Изменения одной пары «пользователь — видео» имеют единый порядок. После подтверждения S2 или S3 последующее чтение S4 с требованием соответствующей версии возвращает это состояние или состояние более нового изменения. Так пользователь читает результат собственной записи. При отсутствии более нового изменения успешно подтверждённый лайк не может самопроизвольно исчезнуть при отказе одного узла или одной зоны.

**Общий счётчик.** Для него допускается согласованность с задержкой: личная кнопка уже может быть активна, когда публичное число ещё не выросло. В штатном режиме и при заданном пике не менее **99,9% подтверждённых изменений** должны быть отражены в выдаваемом общем счётчике в течение **5 секунд**, а остальные — не позднее **30 секунд**. Задержка измеряется от подтверждения изменения до его отражения в публичных чтениях из обслуживающих регионов.

Ответ S1 содержит время, по которое обработаны изменения. Во время сбоя допускается вернуть более старое значение, но его возраст не должен превышать **60 секунд**; такой ответ считается деградировавшим и не засчитывается как успешный для целевой доступности, если нарушена обычная свежесть. При возрасте больше 60 секунд возвращается ошибка временной недоступности. Интерфейс может явно показать время актуальности деградировавшего значения.

К завершению указанного RTO обслуживание S1 должно восстановиться с обычными требованиями к свежести. Восстановление счётчиков, используемых для публичных ответов, входит в RTO. Повреждённые копии, не участвующие в обслуживании, могут восстанавливаться в фоне до **10 минут после восстановления обслуживания** при входящем потоке не выше заданного пика; до проверки их не используют для S1. Повторная обработка одного изменения не должна оставлять постоянную ошибку в счётчике.

## Сохранность и восстановление

Источник истины — сохранённые состояния пользовательских реакций. Агрегированный счётчик должен быть восстановим из них: потеря производной копии счётчика не означает потерю самих лайков.

| Событие | Допустимая потеря подтверждённых изменений, RPO | Восстановление обслуживания, RTO |
|---|---|---|
| Отказ одного узла или одной зоны основного региона | **0**: подтверждённые реакции, их версии и записи дедупликации сохраняются | S1 ≤ 1 минуты; S2–S4 ≤ 5 минут |
| Полная потеря основного географического региона | Не более **60 секунд** подтверждённых изменений перед аварией | S1–S4 ≤ **30 минут** в резервном регионе |

RPO обозначает допустимый объём потерянных данных, выраженный временем последних изменений. RTO обозначает максимальное время восстановления обслуживания после возникновения отказа, включая обнаружение. Обнаружение отказа должно занимать не более **30 секунд**. К завершению RTO ответы должны соответствовать обычным требованиям к содержимому, свежести и предельному времени; выдача только ошибок или устаревших счётчиков не считается восстановлением обслуживания.

При полной потере региона требование RPO = 0 не заявляется: допускается потеря последних 60 секунд подтверждённых изменений вместе с соответствующими метаданными. Версия потерянного изменения не должна заменяться успешным ответом с меньшей версией. После переключения клиент получает явную ошибку для такой версии и может прочитать восстановленное состояние без этого условия.

Версия включает идентификатор поколения восстановления; после аварийного переключения номера утраченных версий не переиспользуются. Запросы изменения также указывают известное клиенту поколение. При его смене сервис сначала проверяет сохранённую запись дедупликации. Известный повтор получает исходный результат без повторного изменения. Если запись отсутствует, запрос со старым поколением отклоняется с уведомлением о восстановлении; клиент сначала перечитывает текущее состояние и затем при необходимости создаёт новое действие. Это явное исключение для потерянного окна при полной потере региона; при отказе узла или зоны гарантии FT5 и FT6 сохраняются полностью.

Реакции хранятся до снятия лайка или удаления связанных пользователя либо видео. Удаление пользователя или видео поступает как доверенное событие от видеохостинга; связанные реакции удаляются из оперативных данных и исключаются из счётчиков не позднее **24 часов**. Это вспомогательная операция жизненного цикла, а не отдельный основной пользовательский сценарий. Недоступное или удалённое видео перестаёт обслуживаться как существующее сразу после получения соответствующего события.

Резервные копии создаются не реже одного раза в сутки и хранятся **30 дней**. Они защищают от повреждения или ошибочного изменения данных и не являются механизмом достижения RPO ≤ 60 секунд при потере региона. Возможность восстановить реакции и пересчитать счётчики из резервной копии должна проверяться не реже **одного раза в месяц**. Одновременная полная потеря обоих регионов не входит в модель гарантируемого восстановления.

## Географические ограничения

Целевая аудитория проекта — пользователи европейского региона. Обслуживающие данные размещаются в **двух независимых географических регионах в Европе**, расположенных не ближе **300 км** друг от друга. Основной регион принимает изменения реакций; резервный регион обеспечивает восстановление при его потере. В штатном режиме чтение общего счётчика может обслуживаться из обоих регионов при соблюдении требований свежести.

Пользовательские реакции и резервные копии не размещаются за пределами выбранных европейских регионов. Синхронное подтверждение каждой записи между удалёнными регионами не требуется; это согласуется с допустимой потерей последних 60 секунд при полной потере основного региона. Внутри основного региона подтверждённые изменения должны выдерживать отказ одной зоны без потери.

Целевые задержки относятся к указанной границе API в обслуживающем регионе. Для пользователя, находящегося далеко от Европы, те же значения полной задержки по интернету не обещаются. Расширение географии пользователей потребует пересмотра профиля нагрузки и соответствующих требований.

## Проверка согласованности требований

Главный сценарий S1 требует быстрого массового чтения и допускает ограниченную задержку общего счётчика. Сценарии S2–S4 требуют правильного состояния конкретной реакции и сохранения подтверждённых изменений в заданной модели отказов. Поэтому личное состояние и публичный счётчик не обязаны обновляться одновременно.

Повторное выполнение уже активного лайка, дедупликация исходной операции и порядок разных действий описаны отдельно. Это предотвращает дополнительный учёт одной реакции и восстановление старого лайка из-за запоздавшего ретрая после его снятия.

Требование RPO = 0 ограничено отказом одного узла или одной зоны. Для полной потери основного региона заданы отдельные RPO и RTO. Отказ записи при невозможности надёжного подтверждения считается ошибкой доступности; корректность не достигается скрытым исключением таких запросов из метрик.

Требования покрывают все четыре сценария и заданы вместе с профилем нагрузки, объёмом данных, границей измерения и географией. Расчёт ресурсов, выбор конкретных технологий и подтверждение этих целей экспериментом выполняются на последующих этапах курсового проекта.
